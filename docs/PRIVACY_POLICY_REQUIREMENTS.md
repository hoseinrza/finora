# Privacy policy requirements

This document is an internal reference for whoever writes/publishes Finora's public-facing
privacy policy (required by the Play Console before this app can request the permissions below).
It is not the policy itself - it's the factual inventory of what the app actually does, so the
policy text can be accurate.

## 1. Permissions requested and why

| Permission | Purpose | Data touched |
|---|---|---|
| `RECEIVE_SMS` | `BankSmsReceiver` reads the broadcast extras of incoming SMS to detect bank transaction messages (deposits/withdrawals) and auto-log them as transactions. The app does **not** request `READ_SMS` and never queries the SMS inbox/content provider - it only ever sees the SMS broadcast at the moment it arrives. | SMS message body, for bank-pattern SMS only |
| `POST_NOTIFICATIONS` (API 33+) | Shows a local status-bar notification when a transaction is auto-detected. | Notification title/text only; no data leaves the device |
| `BIND_NOTIFICATION_LISTENER_SERVICE` (special access, user-granted via Settings, not a manifest runtime permission) | `BankNotificationService` reads the title/text of notifications posted by other apps (e.g. banking apps) to detect transactions the same way SMS is parsed. This is a system-level access the user explicitly grants per-app in Settings, separate from the standard runtime permission dialog. | Notification title/text of **all** notifications posted while the listener is active, filtered in-app to bank-pattern text only; non-matching notifications are discarded and never persisted |

## 2. Data collected, purpose, and storage

| Data | Source | Purpose | Where stored | Leaves the device? |
|---|---|---|---|---|
| Transaction records (title, amount, type, category, payment method, account name, date, free-text description including up to 100 characters of the original SMS/notification text) | User manual entry, or auto-extracted from SMS/notifications via `BankParserUtils` | Core app functionality: transaction history, budgets, dashboards | Local Room database only | No |
| Budgets, saving goals, accounts/wallets | User manual entry | Core app functionality | Local Room database only | No |
| In-app notification log (alerts/milestones/reports generated by the app itself) | Generated locally by the app | User-facing activity feed | Local Room database only | No |
| Raw SMS/notification text (truncated to 100 chars, embedded in the transaction's `description` field) | SMS broadcast / NotificationListenerService | Lets the user see what raw message a transaction was extracted from | Local Room database only | No |
| Crash/error reports (stack traces, device model, OS version - standard Crashlytics payload) | Firebase Crashlytics SDK, only when a `google-services.json` is configured | Diagnose and fix production crashes/errors | Firebase Crashlytics (Google Cloud, per Firebase's own data processing terms) | **Yes** - to Firebase/Google |

**There is no backend server operated by this app.** All financial data (transactions, budgets,
goals, accounts) is stored exclusively on-device. The only outbound data flow is crash/error
diagnostics via Firebase Crashlytics, and only if the release build was configured with Firebase
(`google-services.json` present at build time).

## 3. Data retention

- All financial data persists locally until the user deletes it (per-item delete, already
  implemented for transactions/budgets/goals/accounts/notifications) or uninstalls the app.
- There is no server-side retention because there is no server.
- Crashlytics report retention follows Firebase's standard retention policy (Google-controlled,
  not app-controlled) - link to Firebase's data retention terms in the published policy.

## 4. Data sharing

No financial data is shared with any third party. The only third-party processor involved at all
is Firebase/Google, and only for crash diagnostics (see above) - never for transaction/financial
data.

## 5. User rights / controls to document in the policy

- Users can delete any individual transaction, budget, goal, account, or notification from within
  the app (swipe-to-delete).
- Uninstalling the app removes the local encrypted database entirely (standard Android app-data
  removal on uninstall, subject to `android:allowBackup="true"` - see note below).
- There is no account/login system, so there is no server-side account to delete separately.

## 6. Play Console declarations this app will need

- **SMS/Call Log permissions declaration form**: required because the app requests `RECEIVE_SMS`.
  Core use case to declare: "automatic bank transaction logging from SMS." (Note: removing the
  unused `READ_SMS` permission, done in this change, narrows the scope of what needs to be
  justified.)
- **Data safety section**: declare "Financial info" (transactions) as collected but *not shared*,
  stored on-device, user can request deletion (in-app). Declare "Crash logs" / "Diagnostics" as
  collected and shared with Firebase/Google if Crashlytics is enabled for the shipped build.
- **Privacy policy URL**: mandatory once any permission above is requested; must be a live,
  publicly reachable URL at submission time.

## 7. Open item to flag to product/legal before publishing

`android:allowBackup="true"` in `AndroidManifest.xml` (unchanged by this audit) allows Android's
Auto Backup to include app data in a user's Google account backup, including the local database
file (which is not encrypted at rest). This should be explicitly reviewed and called out in the
policy rather than left implicit.
